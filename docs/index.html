Abstract

Which existing pages should a content reviewer look at first, when the team can only review a limited number of pages per week? 16,726 visible pages from FlyRank's starter search-performance dataset were scored first with a transparent hand-written rule (CTR relative to position, plus staleness), then with a random forest trained on 28 pre-decision features and validated with 20 repeated client-holdout splits. The model beats the baseline's discrimination on 90% of splits (mean ROC-AUC 0.642 vs. 0.573) and its top-of-queue precision on 75% of splits (Precision@50 0.785 vs. 0.717) — a real but modest gain, with a wide spread across splits. The output is a ranked review queue with a reason code, an action label, and a confidence level per page: decision support for a human reviewer, not an automated publishing decision.

1Introduction

A content team with limited review capacity cannot look at every page every week. The question this project answers is narrow on purpose: given a fixed number of review slots, which pages should fill them first? The decision this supports is the composition and order of a weekly content-review queue. The action a human takes from the output is one of two things — rewrite a weak title or meta description (review_title_snippet), or leave the page for now (monitor). The cost of getting this wrong runs in both directions: a false positive spends a reviewer's scarce time on a page that did not need it, at the real cost of a page further down the queue that did; a false negative lets a genuinely declining, high-demand page keep losing visibility unnoticed. Because capacity is the binding constraint, this is a ranking problem — precision at the top of the list matters far more than accuracy averaged across every page a client owns.

2Data

This project uses the starter dataset shipped with the FlyRank ML internship repository (data/raw/content_refresh_anonymized.csv) — 30,000 pseudonymized page-level rows across 32 clients, one row per content page over a trailing 90-day window. This is the lane's own default dataset per the internship's lane guide. All identifiers (content_id, client_id) were already scrambled by FlyRank before release and are used here only to group pages by client for validation splits — never as model inputs, and never shown identifiably anywhere in this paper.

Deliberately excluded: the trend_direction and trend_pct columns, because they define this project's proxy label directly — using them as model inputs would let the model read the answer rather than predict it. The four 30-day trend columns (impressions_last_30d/prev_30d, clicks_last_30d/prev_30d, sessions_last_30d/prev_30d) are excluded for the same reason — they are the mechanical inputs to that label. A code assertion in the capstone notebook confirms none of these ever enters the feature matrix. No client name, domain, URL, or raw query text appears in this paper, the repo, or the underlying notebooks.

Visible pages only: the dataset is filtered to pages with at least 500 impressions in 90 days and a real average search position (16,726 of 30,000 rows). A page nobody sees is a discoverability problem, not a refresh-review problem, and mixing the two would confuse the label.

3Methodology

3.1 Baseline

Before any model was built, two candidate signals were checked against the data directly. CTR relative to a page's own position tier was confirmed: the decline rate falls in a straight step pattern from 0.682 to 0.518 as relative CTR rises across five buckets (n = 2,907 to 4,312 per bucket). Staleness (days since last update) was mixed: stale pages decline more overall (+0.096), but the gap shrinks by half once compared inside each client (+0.053, and only 9 of 13 qualifying clients showed it at all) — evidence that part of the raw effect is a client pattern, not a page one. The baseline rule that follows from this evidence is score = 100 × (0.8 × ctr_gap + 0.2 × stale_90) × demand_weight, with a single reason code, low_ctr_for_position, firing when a page's CTR sits under half its position tier's median.

3.2 Features and target

The model reuses the baseline's five inputs (impressions, position, CTR, position tier, days since update) and adds 23 more pre-decision, public-safe signals: content age, active-impression days, content length, keyword-market context (search volume, competition, CPC), on-page engagement and scroll rate, and content type / search intent as categorical context — 28 features in total, with a missing-value indicator kept alongside every feature that has real gaps, rather than silently filling zeros. The target is a proxy, not an observed future outcome: is_declining = 1 when FlyRank's own trend_direction field reads "down" — a same-window bucket, which is why every result below is read as directional association, not causal proof.

3.3 Validation design

Pages from the same client can share a template, a CMS, or a tracking setup, so a plain random split would let a model partly memorize the client rather than learn a genuine page-level pattern. Every split here groups by client_id with whole clients held out (GroupShuffleSplit, 70/30). Because the 32 clients vary widely in size and decline rate, a single split's test-fold base rate is unstable — one observed seed alone gave a test base rate of 0.801, against a 0.576 average across 20 seeds — so every metric below is the mean (and standard deviation) across 20 independently seeded client-grouped splits, rather than a single lucky or unlucky draw.

Error analysis. On one held-out fold, the random forest's top 20 scored pages contained 11 truly declining pages out of 20, and only 4 distinct clients — one client held 14 of the 20 slots. This client concentration recurs at full scale: scoring every visible page and taking the unadjusted top 50 returns a single client, fifty times. That is a concrete, checkable finding, not a hypothetical caveat — see §6.

What the model actually learned

Random forest importances and logistic regression coefficients agree on the core story. ctr and avg_position matter most in both, in the same direction the CTR-vs-position signal check found. content_age_days and impressions_90d are next: older, lower-impression pages are flagged more, agreeing across both models. days_since_last_update carries a small positive weight — real, matching the mixed staleness verdict, but a minor contributor rather than the main driver. One nuanced result worth stating plainly: pages already sitting deep on the results page (position_tier_page_3_5, striking) carry some of the model's largest coefficients almost independent of other signals — that reads more like where the page already is than a fixable content problem.

5Limitations & honest framing

  • The label is a same-window proxy, not an observed outcome. Every finding here is directional — associated with decline in this dataset — never causal, and never a claim that a title fix would reverse a decline.
  • Validated in-sample, on one static snapshot. The 20-split repetition addresses which-clients-land-where noise, but every split still trains and tests on the same fixed dataset; a genuinely new time period (the warehouse-release, time-aware workflow built in the data-contract notebook) is the stronger test this result still needs.
  • 32 clients is a small, unbalanced panel for a client-holdout design — some test folds saw only a handful of clients, which is exactly why Precision@50's spread across splits (±0.140) is wide.
  • The gain over baseline is real but modest (AUC 0.642 vs 0.573): useful for ordering a review queue, not a confident diagnosis of any single page.
  • No causal claims and no claims about Google's algorithm. This paper ranks candidates for human review. It does not claim a title fix reverses a decline, and it makes no claim about how any search engine actually ranks pages.

6Ranked recommendations

  1. High confidence + low_ctr_for_position → review_title_snippet first — both the transparent rule and the model agree here, and the CTR-vs-position signal check backs it directly.
  2. High model score, no baseline reason code → route to monitor with a note. The model is picking up a broader pattern (age, low impressions for position, weak keyword-market context) the single-signal rule cannot name as specifically — worth a human's eyes, not an automatic rewrite.
  3. Cap per-client concentration before the queue reaches a reviewer. Without a cap, the unadjusted top 50 rows of the deployed queue are all one client — a reviewer would work through one client fifty times before reaching a second. A round-robin or interleave cap on consecutive same-client slots is a policy choice for whoever owns review capacity, not a modeling fix.
  4. Low confidence → leave as monitor; do not spend scarce review time here.

This ranking should be checked against real review capacity: if a team can act on 50 pages a cycle, only the top 50 by model score — after the per-client cap above — should enter the queue, in that order.

7Reproducibility

Every notebook referenced in this paper is committed under work/notebooks/ in the linked repository, and the exact metrics in this paper were produced by re-running the capstone notebook, not rounded or adjusted afterward.

git clone https://github.com/Ssaqlain09/flyrank-ml-internship
cd flyrank-ml-internship
pip install -r requirements.txt scikit-learn
jupyter nbconvert --to notebook --execute --inplace work/notebooks/capstone.ipynb

Random state is fixed throughout: GroupShuffleSplit(random_state=seed) for seed in range(20), and RandomForestClassifier(random_state=42) with a class-balanced logistic regression for every fit. The notebook regenerates work/outputs/capstone_ranked_queue.csv (16,726 rows) on every run — the data file itself is gitignored by design, but work/capstone_report.md and work/outputs/baseline_metrics.json are committed receipts that can be checked against a fresh run.

Relevant notebooks: work/notebooks/w03_data_contract.ipynb (data contract and leakage trap on the full warehouse release), work/notebooks/w04_baseline_score.ipynb (baseline signal checks and rule), work/notebooks/capstone.ipynb (this paper's model, validation, and final queue).
